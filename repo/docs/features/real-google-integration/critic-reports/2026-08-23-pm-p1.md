## Findings

### F1 (significant) — Topic creation is not covered by duplicate prevention; reruns will still duplicate topics

**Where:** §6 (Duplicate prevention — product requirements), §9 (Transfer
engine row, "Keep... Topic infrastructure first... No re-architecture"), §4
(Value proposition: *"Run it as many times as you like — assignments that
already exist in the destination are skipped, not duplicated."*)

The dedupe rule in §6.1 is scoped explicitly to CourseWork and
CourseWorkMaterial ("same coursework surface... CourseWork↔CourseWork;
CourseWorkMaterial↔CourseWorkMaterial"). Topics are out of that definition by
construction, and the reconciliation invariant explicitly excludes them
(confirmed in `docs/product/04-architecture.md` line 1237:
`topicsCreatedOrMapped` absent from the sum; and the topic-map build step
"Build the old->new topic ID map first" calls `createTopic` for every source
topic unconditionally, with no existing-topic-by-name check anywhere in v1's
design).

Net effect: on a second run against the same destination, coursework items
will correctly skip as duplicates, but topics will be recreated every time —
a teacher who reruns after a partial failure (the brief's own stated primary
scenario, §1: *"a teacher who re-runs after a partial failure... doubles
their target course"*) will end up with duplicate topics (two "Unit 1"
sections) even though the assignments inside them are correctly deduped. This
directly undercuts the phase's headline value proposition and the JTBD
*"When I run it twice, don't double my course."*

This won't be caught by the reconciliation invariant (topics are deliberately
outside it) or by the new §6.6 fixture (which only exercises
coursework-surface matches). It will only surface as a real teacher's visible
duplicate-topic list after a live rerun — exactly the failure mode this phase
exists to close.

**Fix:** Either (a) extend §6's duplicate-prevention scope to topics
(name-normalized match against existing destination topics before
`createTopic`, feeding the same or a sibling accounting), explicitly stating
this in §6.1 and adding a topic case to the §6.6 fixture, or (b) if topic
dedup is deliberately out of v1-of-phase-2 scope, say so explicitly as a named
non-goal in §6.7/§10 with the reasoning, so it isn't silently absent. Silence
is the one option that should not survive to UX/architecture.

### F2 (significant) — Precedence between a duplicate-title match and a health-check-driven outcome on the same item is unspecified

**Where:** §6.3 ("When detection happens"), §6.6 (fixture requirement)

The pre-flight scan now does two things to the same item set: the existing
health check (trashed/permission-locked attachments → action-sheet
fix/skip options) and the new duplicate-title check (§6.3). The brief never
states what happens when both conditions are true for the same source item —
e.g., a source post whose title normalizes to match an existing destination
draft, and whose attachment is also trashed. Does the duplicate skip
short-circuit before the item ever reaches the action sheet (the item will be
skipped regardless of attachment health, so surfacing it in the action sheet
would be pointless and confusing), or does the existing health-check flow run
first and the duplicate check apply only to items that clear it? Either
answer is defensible, but it is a product-semantics decision (what the
teacher sees, and whether they're asked to resolve an attachment issue for an
item that's going to be skipped anyway), not a mechanism detail for the
architect to invent. The new §6.6 fixture list doesn't include a combined
case either, so this gap would also go untested.

**Fix:** Add one sentence to §6.3 stating precedence (recommended: duplicate
detection short-circuits — a title match skips the item outright and it never
enters the action-sheet surface, since fixing an attachment on an item that
won't be created has no value), and add a combined-case row to §6.6's
fixture list.

### F3 (significant) — The testing-mode "100 test users" figure is stated as fact without its own inline MANUAL-VERIFY tag

**Where:** §8, "The verification gate" paragraph: *"the app runs in testing
mode with up to 100 explicitly-listed test users."*

The brief's own Assumptions section states the discipline it's supposed to
follow: *"Real-API behavior facts asserted from model knowledge (default
`courseWorkStates`, scope names/classifications, testing-mode 100-user cap)
are load-bearing and individually marked MANUAL-VERIFY where cited."* Two of
the three examples it names (`courseWorkStates` default in §6.1, scope
classifications in §8) are in fact tagged inline at their point of use. The
third — the 100-user testing-mode cap — is not; it reads as an established
fact in §8's body text, and the reader only learns it's model-knowledge by
separately reaching the Assumptions section at the bottom of the document.
This is precisely the failure mode the review was weighted to catch: a
load-bearing Google API fact stated from model knowledge should not be
distinguishable from a confirmed one only by cross-referencing a different
section.

**Fix:** Add an inline `**MANUAL-VERIFY:**` tag at the sentence in §8, matching
the treatment already given to the other two facts in the same section.

### F4 (minor) — One Directions/reality tension resolved silently, not named as a conflict

**Where:** `inputs/directions.md` §1: *"Store user session/tokens securely and
pass Google access tokens to server routes for API calls"* vs. brief §7.1e:
*"Tokens are stored server-side... Access tokens are never exposed to the
client bundle."*

The Directions' phrasing is ambiguous enough to be read as instructing that
access tokens flow through client-facing routes. The brief's resolution
(server-side-only storage, never exposed to the client) is clearly the
correct and safer reading, and is not in tension with any binding decision —
but it's a place where the Directions text could mislead a less careful
implementer, and the brief's own C1–C6 table exists precisely to name and
retire this kind of ambiguity. It wasn't given a C-number. Low severity
because the resolution reached is right regardless; flagged only because the
brief holds itself to a standard of naming these explicitly and this one
slipped through the naming (not the resolving).

**Fix:** Optional — add a seventh row (C7) to §0's conflict table, or fold a
clause into C1/§7.1e noting the ambiguity was resolved in favor of
server-side-only custody, for the audit trail's sake.
