### 2. The 7-tile layout — does NOT survive verification as written (F2, P0)

`tokens.css` (confirmed at lines 285–287) defines exactly two tiers for the
existing 5-tile `.stat-grid`: `max-width:1024px → repeat(3,1fr)`,
`max-width:768px → repeat(2,1fr)`.

The artifact's §3.2 CSS block for the new 7-tile, two-group layout contains
**only one** `@media` rule:

```css
@media (max-width: 1024px){
  .stat-group-grid, .stat-group-grid.topics-group{ grid-template-columns:repeat(2,1fr); }
}
```

Immediately above that block, the artifact's own comment says: *"Same two
breakpoints as v1's 5-tile strategy — reused, not reinvented."* That claim
does not match the code beneath it — only the 1024px tier is used; the 768px
tier is dropped entirely (both groups jump straight to 2-col at 1024px and
stay there). This is an internal inconsistency between prose and CSS, not
necessarily wrong as a design choice, but stated inaccurately.

**More seriously, the produced mockup contradicts both the direction doc and
`tokens.css`.** `docs/features/real-google-integration/mockups/phase2-ui-mockups.html`
line 97 implements:

```css
@media (max-width: 620px){
  .stat-group-grid, .stat-group-grid.topics-group{ grid-template-columns:repeat(2,1fr); }
}
```

**620px appears nowhere in `tokens.css` and nowhere else in the direction
doc.** This is a third breakpoint value, invented in the mockup, directly
contradicting the direction doc's own §6 claim — *"No third breakpoint is
introduced anywhere in this phase"* — and Decision 1's claim of reusing the
system's existing two-tier strategy. The two co-produced artifacts (the spec
and its own mockup) disagree with each other on the exact mechanic this
assignment asked to be checked.

**Recommendation:** either (a) restore the genuine two-tier response (1024px
→ some intermediate arrangement, 768px → 2-col, matching what the prose
claims) or (b) if a single 2-col breakpoint really is sufficient, correct the
prose to stop claiming "two breakpoints reused" and correct the mockup to use
the same value the direction doc specifies (1024px), not 620px. Whichever is
chosen, the direction doc's CSS and the mockup's CSS must agree on the number.

The manifest/ledger concept itself is preserved by the two-group regrouping —
that part of the design response is sound and well-reasoned (Decision 1,
correctly rejecting the naive `repeat(7,1fr)` row extension). The finding is
about the breakpoint value, not the grouping idea.

### 3. Duplicate-vs-user-skip distinction across surfaces — mostly holds, one real gap (F1, P0)

Checked against the itemized log, stat tiles, filter dropdown, and CSV export
as instructed:

- **Log column / pill:** holds — `OutcomePill`/`OutcomeIcon` get an additive
  `skipReason` prop, single source of truth, verified against the actual
  current code (`client/src/components/shared/OutcomeIcon.tsx` today keys
  only on the 4-value `Outcome` enum — exactly the gap the artifact's P0
  Delta describes).
- **Stat tiles:** holds — two visually and structurally distinct tiles
  (§3.2/§3.3), not a recolor.
- **Filter dropdown:** holds — five options up from four, exact wording
  matches the UX wireframe.
- **CSV export:** holds — `buildLogCsv` in
  `client/src/features/summary/CompletionSummary.tsx` today builds its
  `Outcome` column from `OUTCOME_TEXT[item.outcome]`, i.e. exactly the coarse,
  non-`skipReason`-aware lookup the artifact's Delta identifies. The
  instruction ("CSV must call the same skipReason-aware label function the
  on-screen column uses, not a second implementation") is correct, specific,
  and actionable. Good catch — this is exactly the kind of place a
  distinction quietly dies in export while surviving on screen, and the
  artifact closes it.

**The one place the distinction does not survive is the reconciliation
line's arithmetic (§3.2), which is new terrain the "extends to CSV" check
above didn't originally target but the assignment's "check the math" framing
does.** The current, shipped reconcile line (`CompletionSummary.tsx`'s own
code comment) sums exactly **three** terms — `transferred + fallbackShell +
skippedTotal == totalItems` — where `skippedTotal` is a server-computed
aggregate that, by construction (`server/src/services/reconciliation.ts`,
confirmed by reading it), always equals
`skippedByUser + skippedBySystem`. That aggregate is safe by construction: it
can never fail to reconcile, regardless of how many skip sub-reasons exist.

The artifact's new formula replaces this with a **hardcoded four-term**
version: `32 + 2 + 5 + 1 = 40` (transferred + fallback + duplicate-skip +
user-skip). This is only correct when `skippedBySystem == 0`. The artifact
itself, two paragraphs later in §3.3, explicitly acknowledges that
system-interrupted skips (`provider_error`/`server_interrupted`/
`rate_limit_exhausted`) still exist, are out of this phase's scope for the
pill/filter treatment, and keep the pre-existing generic "Skipped" handling —
but it never revisits whether those items still have a place in the
reconcile-line sum. They don't, as specified: the four-term formula has no
slot for them. The moment a real transfer has one or more
`skippedBySystem` items (a named, non-hypothetical case — it's the subject of
this same document's own open P1 Delta about the filter dropdown), the
visible ledger arithmetic will not sum to the stated total, even though the
underlying invariant still holds server-side. That is precisely the failure
mode the artifact itself warns against citing the codebase's own discipline
("a second implementation of the sum is exactly how a ledger starts
disagreeing with itself") — the reconcile line has become a second
implementation of the sum, and it disagrees with itself the moment
`skippedBySystem > 0`.

**Recommendation:** either add a conditional fifth term to the reconcile line
(shown only when `skippedBySystem > 0`, using the existing `systemSkipLine`
copy or a short label) so the visible sum always equals `totalItems`, or keep
the reconcile line anchored to the safe `skippedTotal` aggregate (as today)
and let the stat tiles present the duplicate/user breakdown without claiming
the breakdown itself is what the reconcile line sums. This is architect/
engineer-facing and should be added to the artifact's Deltas table as a P0,
alongside the existing `TransferJobStatus` schema gap it's adjacent to.

### 4. The no-Tailwind guard — independently re-scanned, artifact's finding holds (no third file)

Ran a broad, shape-based scan (not the diagnosis's five literal substrings)
across all 35 `.ts`/`.tsx`/`.jsx` files under `client/src`, matching Tailwind-
shaped class prefixes: `bg-`, `text-`, `border-`, `rounded(-*)`, `shadow(-*)`,
`flex`, `items-*`, `justify-*`, `w-`/`h-` + numeric, `p[xytblr]?-`/`m[xytblr]?-`
+ numeric, `min-h-`, `max-w-`, `gap-`, `font-weight` keywords, plus a second
pass for `rounded-full`, `bg-white`/`bg-black`, `text-white`/`text-black`,
`w-full`/`h-full`, `inset-`/`top-`/`left-`/`right-`/`bottom-` + numeric,
`divide-`, `ring-`, `animate-`, `transform`/`translate-`/`scale-`/`rotate-`.

Result: **exactly two files match** — `client/src/features/auth/
SignInLanding.tsx` and `client/src/features/auth/AuthFlow.tsx` — the same two
the artifact names. Every other file's `className` values (manually inspected
across 12 additional files a looser first-pass grep flagged as false
positives) are token-system BEM-style classes (`stat-tile`, `outcome-pill`,
`account-row`, `disclosure-body`, etc.), not Tailwind. **No third affected
file exists.** The artifact's own correction of the B15 diagnosis (from "one
file" to "two files") is itself complete — there is no fourth iteration of
this defect waiting to be found. The artifact's proposed guard pattern
(`\b(bg|text|border|rounded|shadow|flex|items|justify|w|h|p|m|px|py|mx|my|gap|
min-h|max-w)-`) is genuinely shape-based, would catch both known files, and
is a reasonable guard specification. This criterion passes.

### 5. Google sign-in button branding — reasonable, appropriately hedged

Colors, approved CTA text, logo non-alteration, and the 44px hit-area
reasoning are consistent with Google's published branding guidance as
described in the artifact. The places where the artifact cannot be fully

non-negotiable brand requirement inside an internal design system — no
finding here.

## Additional findings (lower severity)

**F3 — ARIA role choice for new error/interrupt surfaces is inconsistent with
the project's own established convention (minor-moderate).** The mockup gives
`.signin-error` `role="status"` (implicit `aria-live="polite"`). Elsewhere in
this codebase, `role="status"`/`aria-live="polite"` is reserved for benign,
self-resolving content (`ColdStartOverlay`'s `.coldstart`,
`PreflightScreen`'s `.scanning`), while genuine error conditions use
`role="alert"` (`SelectionScreen`'s `.field-error`, `TransferProgress`'s
cancel-confirm `.notice`). A sign-in failure is an error, not a status
update, and the direction doc's own prose never specifies a role for
`.signin-error` at all — only the mockup picked one, without reconciling it
against the codebase's existing alert-vs-status split. Separately, the
mockup's `.interrupt-banner` (4b/4c) carries no `role`/`aria-live` attribute
at all. The artifact's mitigating mechanism — moving focus to the banner/
heading on mount (§6) — is a legitimate alternative to a live region (a focus
change is itself announced), but the doc should say so explicitly for these
two components rather than leaving the ARIA semantics to be inferred or
picked ad hoc in the mockup.

**F4 — Decision-recording undercounts what the artifact claims (minor).** The
artifact's "Decisions (confirmed)" section lists 13 numbered items and states
they were "Recorded via `stage_record_decisions`... (batch call, this
session)." `state.json`'s `stages.ui.decisions` array contains **10** entries.
At minimum, decision #12 ("Imagery: none needed") has no corresponding
state.json entry; #4 (glyph choice) and #6 (inline-vs-full-page failure
placement) appear folded into broader recorded questions (#3 and #4 in
state.json respectively) rather than recorded standalone. Not blocking, but
the claim slightly overstates what actually landed in the durable decision
log — worth a quick pass to record the missing one(s) if state.json is meant
to be a complete audit trail.

**F7 — Minor overstatement of pairing reuse (cosmetic).** §3.3 says the new
teal duplicate-skip treatment "is the same pairing already used for
`.badge-sis` and the Action Sheet's 'Recommended' stamp." True for
`.badge-sis` (exact match: `--teal-700` text/border + `--teal-100` fill,
confirmed in `tokens.css`). Only partially true for `.stamp`, which uses
`--teal-700` text/border but **no** `--teal-100` fill (transparent,
inherits ambient background) — confirmed in `tokens.css` lines 242–246. Does
not affect the contrast math or the design rationale; just imprecise as
stated.
