## Findings by criterion

### 1. Completeness — F1 (APPLY, moderate)

**§7's "at minimum" inline-troubleshooting list omits B7 (PostgreSQL
provisioning), which PM brief §7.3 explicitly names as required checklist
content.**

PM brief §7.3: "...Render backend env vars; Render static-site build with
`VITE_API_BASE_URL` and the rebuild-on-change rule (B14); `CORS_ORIGINS`
including the custom `X-Classroom-Copier` header allowance (B10);
'verify both Render services point at the same GitHub repository' (B11); **
PostgreSQL provisioning on Render (B7)**; and what success looks like at each
step (... B9 ... B8)."

UX §7 item 3's "at minimum" bullet list translates B11, B13, B9, B14, B8, and
B10 into plain-language checklist content — but not B7. B7 in the bug
inventory is exactly the class of silent-failure-mode this checklist exists to
prevent (`DATABASE_URL` defaulting to ephemeral SQLite instead of a
provisioned Postgres instance) and is the same severity/shape as the six items
that *are* included. Given how heavily this review weights the checklist
being genuinely actionable by a non-developer, a missing gotcha of this kind
is a real gap, not a nitpick.

**Fix:** add one bullet to §7 item 3's list, e.g.: "Your database needs to be
a real Postgres database provisioned on Render — not the default SQLite
setting — before the backend will boot cleanly (B7)."

### 2. The Deltas / zero-silent-drop completeness — F2 (APPLY, moderate)

**Delta P0-2's "fail outright" branch has an unaddressed reconciliation
question that the doc's own zero-silent-drop language doesn't resolve.**

§5, wireframe 4c, and the Open Questions all correctly leave the
pause-and-wait-vs-fail-and-let-a-rerun-recover choice to the architect. But
the doc states the requirement as "every item must still resolve to a defined
transferred/fallback/skipped outcome by job completion" — and if the
architect picks "fail outright," it's not obvious how an unattempted item
(never reached before the token died) resolves into one of exactly those
three buckets in *this* job's Completion Summary without introducing a new
skip-reason value (e.g., "Google access needed to be reconnected"). If that
happens, the same two-tile/distinct-wording/distinct-filter treatment
Delta P0-3 mandates for `duplicate_title` vs. `skippedByUser` would need to
extend to a third skip reason — and nothing in the doc anticipates that.

This doesn't need to be resolved here (it's legitimately architect scope,
consistent with the doc's own discipline elsewhere), but it should be named
as an explicit open question rather than left for the architect to discover
on their own that "fail outright" and "the closed skip-reason vocabulary"
are in tension.

**Fix:** add one line to Open Questions: "If the architect chooses
fail-outright over pause-and-wait, whether unattempted items need a new
skip-reason value (and therefore P0-3's distinguishability treatment) to stay
inside the closed transferred/fallback_shell/skipped vocabulary — architect
scope, but flagged so it isn't discovered late."

### 3. Failure-path completeness — F3 (APPLY, minor)

**No explicit statement closes out "user closes the browser tab/window mid
sign-in without clicking Deny"** — one of the failure paths this review was
asked to weight heavily by name. Given Decision 1 (full-page redirect, not a
popup), this is very likely a non-issue by construction — there is no parent
app tab left waiting on a `postMessage` the way there would be in a popup
flow; closing the browser just means the user never returns, and the next
visit re-runs the ordinary session check. But the doc doesn't say this
explicitly the way it does for the Back-button edge case (§2, architect-
flagged) or the Google test-user block (§5) — it's left to be inferred from
the popup-vs-redirect decision rather than stated as closed.

**Fix:** one sentence in §5, parallel to the Back-button treatment: "Closing
the browser mid-redirect is not a distinct failure state under the full-page-
redirect model (Decision 1) — there is no parent tab waiting on the popup to
resolve; the user simply returns (or doesn't) to an ordinary signed-out
landing screen on their next visit."

### 4. Prior-artifact coherence — F4 (APPLY, minor)

**Next Handoff doesn't flag that the Completion Summary's stat-tile count
grew from 5 (v1) to 7 (this phase).** v1's UI direction
(`docs/product/03-ui-direction.md`) specifies "five stat tiles in a single
row" as a concrete layout decision. This phase's wireframe 3a shows 7 tiles
(topics split into created/reused, skips split into duplicate/user-chosen).
The Next Handoff section correctly flags that the two skip tiles need
*visually distinct treatment*, but doesn't flag that the *tile count itself*
has grown past the row-layout assumption baked into v1's design direction —
a different, layout-level problem UI needs to solve, not just a coloring one.

**Fix:** add a line to Next Handoff: "Stat-tile count grows from v1's 5 to 7
(topics split into two, skips split into two) — v1's UI direction assumed
five tiles in a single row; UI should decide whether that still holds or
needs a wrap/grid treatment."

### 5. Clarity — F5 (DEFER, minor)

Decision 11 puts v1's notice language in quotation marks — "superseding v1's
'this check does not exist yet' language entirely" — as if quoting v1's
actual copy. V1's real notice text (per `docs/product/02-ux-workflow.md` and
its wireframe) is "a persistent notice states that re-running creates
duplicate drafts," not that literal phrase. The paraphrase is a fair
characterization of the notice's *effect*, but presenting it in quotation
marks reads as a direct quote it isn't. Low stakes — doesn't affect anything
downstream — but worth a light touch (drop the quotation marks, or replace
with a real short quote) if this doc is revised for other reasons.

### 6. Omission (secondary persona) — F6 (DEFER, minor)

The live-OAuth checklist's test-user pre-flight step (§7 item 4) is framed
around the primary teacher signing themselves in. The doc's own secondary
persona (curriculum lead/co-teacher, carried from v1) would also need to be
added to the OAuth consent screen's test-user list before they could sign in
under the same testing-mode posture — the doc doesn't say whether that's in
scope for the checklist or left implicit. Low severity (a natural corollary
of the same step engineer will already write), but a one-line callout would
close it explicitly rather than leaving it to be inferred.

## What passes cleanly (no issues)

- **P0-3 distinguishability** is genuinely testable everywhere a teacher can
  see outcomes: two stat tiles, distinct Outcome-column wording, a split
  filter dropdown, and an explicit CSV reason-code mapping (`duplicate_title`
  as a new value in the existing reason column). This is exactly the concrete,
  checkable form the review was weighted to look for.
- **Topic reuse reporting** stays outside the item invariant everywhere it's
  shown (pre-flight disclosure, stat tiles, itemized-log exclusion, topic
  detail panel) with an explicit "never counted in the item total" callout —
  matches PM §6.8 precisely.
- **The live-OAuth checklist shape** (numbered/grouped steps, confirmation
  cue per step, inline troubleshooting placed at point of use, pre-flight
  test-user step, concrete success checkpoint, closing "if something doesn't
  work" step) is genuinely usable by a non-developer and correctly scoped as
  UX's job (shape/requirements) vs. engineer's job (as-built content) — no
  CLI, no dev-tools jargon anywhere in it.
- **The three Deltas are correctly scoped as architect decisions.** P0-1 and
  P0-2 both carry explicit "Prerequisite for next stage? Yes" flags naming
  architect as owner; P0-2 in particular states the UX-side contract (every
  item resolves to a defined outcome, no silent drop) without prescribing the
  engine mechanism, which is the right level of specification (see F2 for the
  one gap in that contract).
- **Every named OAuth failure path except "tab closed"** (consent denied,
  expired/invalid link, generic catch-all, cold-backend-interleaved-with-
  redirect, Google test-user block, session expiry mid-wizard, session expiry
  mid-transfer, token-refresh failure mid-transfer, Back-button after
  redirect) is specified with a concrete screen, concrete copy, and a defined
  next action — never a dead end. See F3 for the one gap.
- **Cross-references to the real codebase are accurate** — component names,
  routes, and the v1 architecture's D4 cold-start figures (2s overlay / 60s
  ceiling) all verified against `docs/product/04-architecture.md` and the
  actual `client/src` and `server/src` trees.
