## 6. Engineer's Self-Disclosed Limits — Carried Forward

The engineer disclosed six architectural limits in `05-implementation.md` § 7, and QA re-verified them in `06-qa-report.md` § Cycle 1 §11. **QC does not absorb these into a green verdict; they must be carried forward to the human gate.** QC confirms QA's verification:

### 1. **wcag_aa_automated_per_step is NOT browser-verified**

The specified design called for Playwright + `@axe-core/playwright` for real-browser E2E. This run uses Vitest + jsdom + axe-core instead (browser download was unavailable). **jsdom has no layout**, so axe's own `color-contrast` rule reports as **incomplete**. A deterministic arithmetic WCAG audit was substituted (`client/src/styles/contrast.a11y.test.ts`, checking all 13 token pairings against the WCAG AA contrast formula). This is **stronger for contrast specifically** but **not a browser pass**.

**Caveat:** Do not read `wcag_aa_automated_per_step: PASS` as "real-browser accessibility verified." It means "structural a11y rules verified in jsdom + contrast verified by arithmetic." A future real-browser E2E pass is on the backlog as `[ENGINEER]` high-severity.

### 2. **Nothing has been deployed**

The Render free-tier spin-down / filesystem check was never run. Whether SQLite job state survives a redeploy is unknown. The F12 resumability guarantee is verified at the **HTTP layer only** (polling `/transfer-jobs/:id`). Job state survival across a genuine spin-down (not just sleep/wake) is unverified.

**Caveat:** Resumability is intra-process only until deployment is tested. Pre-decided remedy if disk is ephemeral: Postgres. Backlog item: `[ARCHITECT]` deployment spike before treating durability as guaranteed.

### 3. **No live Google integration**

Mock-first by design (user's directive: "mock any test users and google apis that are blocking… we will revisit the APIs later"). `GOOGLE_PROVIDER_MODE=mock` is the only implemented mode; `RealClassroomProvider` does not exist. The contract-test suite (`classroom-provider.contract.test.ts`) is written against the port interface, not the mock class, so a future real adapter would be a swap, not a rewrite.

**Caveat:** Port fidelity is **asserted** (the contract tests), not **verified** (no real adapter). One undisclosed divergence was caught and fixed in cycle 2 (P0-3: the mock was moving attachments, not copying them). Backlog item: `[PM]` real Google integration follow-on (high).

### 4. **Executor lease is tested against a synchronously-injected race, not two OS processes**

`test/quality/executor-lease.budget.test.ts` injects the reconciler synchronously from inside a mocked provider call, in the same Node process, sharing one SQLite connection. This is a faithful **ordering** test of the conditional writes, not a **concurrency** test of real multi-process SQLite write locking.

**Caveat:** The lease is proved to prevent out-of-order writes in a single process. Whether it holds under genuine concurrent connections from two OS processes is a SQLite write-locking property asserted by construction and not measured. Backlog item: `[ENGINEER]` multi-process harness before the single-active-job guard is described as proved in production (medium).

### 5. **SCHEDULED is a mock-invented CourseWorkState, not mapped to real API**

`SCHEDULED` appears in the mock and contract tests but has no equivalent in Google's real API (which models scheduled posts as DRAFT + scheduledTime). Currently both columns exist in the schema (`status` and `scheduledTime`). The mapping is deferred work for when `RealClassroomProvider` ships.

**Caveat:** This divergence is now **disclosed** in `05-implementation.md` §7 and named by its own contract test (`DECLARED DIVERGENCE — SCHEDULED is mock-invented`). It is on the backlog as `[ENGINEER]` work, not a hidden gap. Acceptance: confirmed disclosed.

### 6. **SQLite has no Prisma enums; structural guarantees are limited**

Closed vocabularies (`outcome`, `skipReason`, `status`, `workType`, `shareMode`) are implemented as String columns + zod validation, not Prisma enums. The two-table per-type split (`CourseWork` vs `CourseWorkMaterial`) and the single-active-job guard (`activeAccountId String? @unique`) are the only structural (schema-level) guarantees. Everything else is code-enforced.

**Caveat:** Two more guarantees were one schema word away and were not taken: `TransferJob.scanId @unique` (replay prevention) and `finish()` with `outcome: 'pending'` predicate (overwrite prevention). Cycle 2's fixes added code-enforced guards for both. This is accepted as disclosed; the point was to list what is structural vs. code-enforced, which the engineer did accurately.

## 10. Recommendation

**READY WITH CAVEATS**

The product is **ready to ship at the HTTP layer** with these non-negotiable caveats:

1. **Accessibility testing is not browser-verified.** The contrast audit is deterministic and stronger for contrast specifically, but `wcag_aa_automated_per_step` must not be advertised as "WCAG AA browser pass" until Playwright E2E lands.

2. **Job state durability across Render free-tier redeploy is unverified.** Do not claim "resumability survives server restart" without first testing the spin-down scenario. Pre-decided remedy if disk is ephemeral: Postgres.

3. **Port fidelity is asserted, not verified.** The contract tests are strong, but one undisclosed divergence was caught and fixed in cycle 2 (P0-3). QC or a future pass should not treat the spot-check as exhaustive; a new real-API adapter should be reviewed by a code auditor before shipping.

4. **SCHEDULED is not mapped to the real Google Classroom API.** This is disclosed and on the backlog; do not hide it in release notes.

5. **The executor lease is not tested under genuine OS-level concurrency.** Single-process race injection is strong; multi-process SQLite contention is untested. Do not claim "proved against concurrency" without a multi-process harness if you need hard SLA guarantees.

6. **Mock-invented data structures exist.** The mock implements behaviors (attachment copying logic, some CourseWorkState values, rate-limit simulation with in-memory state) that will not survive a real-API swap without explicit mapping work.

**If the human gate understands and accepts these caveats, the build is ready to ship.** If any of these caveats change the human's risk calculus (e.g., if job durability across redeploy is a hard requirement), the product should not ship without additional work.
