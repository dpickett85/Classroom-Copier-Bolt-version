### 1. Discipline best practices — issue (significant)

### 6. Omissions — issue (significant), two items

**a) Cold-start has no real fixture, and is cited as if it does.**
The cold-start "waking up server…" state is a named, acceptance-tested

- `wireframes/01-sign-in-and-account-picker.md` says the cold-start overlay's

  cover: modal→page, resumability, 429 exhaustion, rubric bucket, network

Net effect: cold-start behavior is exactly as fixture-uncovered as the two
gaps UX did self-report, but nothing tells QC that. Recommend either (a)
flagging cold-start explicitly in Deltas/Assumptions the same way the other
two gaps are flagged, and dropping the phantom `F:` tag and the dangling "per
Deltas" reference, or (b) if a cold-start simulation fixture is intended,
naming it for real (e.g., propose it alongside the F12 recommendation as a
architect/PM follow-up) rather than citing it as already-defined.

**b) The 429-exhaustion *behavior* was resolved, but the fixture gap under it
was not.** P0-3 (already resolved: bounded retry cap of 5 → guaranteed

But F6 as scoped in the brief is "a deterministic mock condition that returns
HTTP 429 mid-batch" — worded as a single transient rate-limit event resolved
by backoff, not a persistent condition that survives 5 retries. As written,
F6 exercises the *retry-succeeds* path, not the *retry-exhausted-then-fallback*
path the resolved P0 now requires. This is structurally identical to the
resumability gap (P0-2), which got a new fixture (F12) precisely because no
existing fixture could exercise it — but no equivalent fixture extension was
proposed for retry-exhaustion. Recommend the same treatment: either extend F6
to explicitly cover a persistent/exhausting 429 condition, or add a companion
fixture (e.g., F13) alongside F12, so QC has something to certify the
exhaustion→fallback path against. Right now that path is exactly as
untestable as resumability was before F12 — it just wasn't caught.

### 7. Errors — issue (significant, contract-breaking)
Acceptance Scenario #15 ("Completion summary reconciliation") states:

> *(topics created/mapped) + (drafts transferred) + (fallback shells) +
> (user-chosen skips) reconciles exactly to the total number of source posts
> scanned*

This is a category error: **topics are not posts.** Summing a topic count
into a formula that must equal a post count is dimensionally wrong and can
never balance for any course with topics > 0. It also directly contradicts
the worked example one file over, in `wireframes/05-completion-summary.md`,
which shows the reconciliation line as `39 + 2 + 1 = 42 of 42 posts scanned`
— i.e., **drafts transferred + fallback shells + skips only**, correctly
excluding topics (6 in that example). The wireframe is right; the acceptance
scenario is wrong. Compounding the error, Scenario #15 also fails to account
for the already-resolved P0-4 4th count ("rubric notes added") — the
wireframe correctly keeps it out of the sum (rubric-degraded posts are a
subset tag on already-"transferred" posts, not an additive bucket), but
Scenario #15's prose never mentions it, so a reader can't tell whether that
omission is intentional or another gap.

This is the doc's own stated **acceptance contract for engineer and QA**
("Given/when/then scenarios… are the acceptance contract for engineer and
QA"). If implemented literally, it produces a check that can never pass.
**Must fix**: correct Scenario #15 to `(drafts transferred) + (fallback
shells) + (user-chosen skips) = total posts scanned`, drop `topics
created/mapped` from the sum, and add a sentence clarifying that "rubric
notes added" is a non-additive subset count over already-transferred posts,
not a fifth reconciliation bucket.

### 8. Oversights — issue (significant), two items

**a) Reconciliation math for combined outcomes is undefined.** The brief and
UX both establish rubric-degradation as "transferred, not fallback" on the
premise that the rubric and the attachment fail independently. Neither
document says what happens when a **single post is both fallback-shell (e.g.,
its attachment is trashed, so pre-flight routes it to Scenario 2) and
rubric-degraded (its rubric also can't copy)** — e.g., an Assignment with a
trashed attachment AND a license-blocked rubric. Does it count only under
"Fallback shells," only under "Rubric notes added," or both (with the
reconciliation sum still landing correctly)? As currently written, the
"transferred vs. fallback" framing for rubric notes implicitly assumes rubric
failure never co-occurs with attachment failure — an assumption that's never
stated, let alone tested (no fixture in F1–F11 combines F2/F3 with F7). This
needs an explicit rule (recommend: fallback-shell status wins for the main
T/F/S bucket; "rubric notes added" becomes a non-exclusive secondary tag that
can co-occur with any of the three main buckets) stated in the doc, even
though testing it may have to wait for a combined fixture.

**b) Accessibility specification is thin for the two highest-traffic
long-running states, despite claiming WCAG AA.** Three gaps, given the
explicit ask to scrutinize this:
- The batch-transfer "recent activity" ticker can emit up to 50 outcome
  events in ~2 minutes. An `aria-live` region that announces every single
  item risks becoming unusable screen-reader noise (a well-known AA pitfall)
  — the doc specifies that progress uses `aria-live` but never addresses
  throttling/summarization (e.g., periodic count announcements vs. per-item
  announcements).
- Outcome markers are described only as "icons" (checkmark / note / etc.) in
  both the workflow doc and the progress wireframe — no text-alternative
  requirement is stated, which risks an icon-only or color-only status
  indicator (a WCAG 1.4.1/1.1.1 concern for exactly the kind of skim-table UI
  this is).
- No stated focus-management rule for when the Action Sheet Modal closes
  (does focus return to the triggering control?) or when the Completion
  Summary replaces the Progress screen (does focus/announcement move to the
  new heading so screen-reader users know the page changed?). The doc traps
  focus *inside* the modal but doesn't close the loop on where focus goes
  afterward.

Separately: the cold-start detector's underlying mechanism — how the
*client* knows the backend has been idle >15 minutes in order to arm a
"no response within ~2s" timer — is asserted as pure frontend behavior, but
is actually a client/server timing dependency no different in kind from the
resumability question (which correctly got escalated to "architect must
expose X"). Cold-start detection isn't flagged as needing an equivalent
architecture contract (e.g., is idle-tracking client-clock-based, or does the
server expose a "just woke up" signal?). Worth flagging for architect the
same way resumability was.
