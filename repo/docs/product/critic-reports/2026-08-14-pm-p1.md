### 3. Prior-artifact coherence (vs. source PRD) — PASSES, with the caveats below

The three headline resolutions the task asked me to check are all sound:

- **Ordering:** PRD's Rule C5 text is self-contradictory ("reverse chronological order (oldest post first, newest post last)"). The brief correctly resolves this by taking the parenthetical and the stated *effect* ("target topic feed maintains correct chronological ordering") as authoritative over the mislabeled term "reverse chronological," landing on oldest-first ascending. This is the only reading consistent with the PRD's own stated goal — good resolution, not a re-interpretation.
- **`classroom.courseworkmaterials` scope:** Correct catch. The PRD's scope list only names `classroom.coursework.students`, which does not cover the separate CourseWorkMaterials API surface the PRD's own Rule B requires (Materials are explicitly in scope). This is a genuine PRD gap, correctly identified and recorded for the follow-on.
- **`drive.file` for Copy-to-My-Drive:** Correct catch — copying a file into a new file owned by the user is a write operation that `drive.readonly` structurally cannot perform, and the PRD's own scope list hedges with "(or drive.file for permission fixes)" without picking one. The brief picks one and records it. (One nuance for the architect to validate at that stage, not a PM-stage blocker: `drive.file`'s real-world grant model is "files created by the app, or opened via a picker" — whether it actually covers copying a *pre-existing* file the user didn't select through a Picker flow is a genuine open technical question. The brief already hedges this correctly by keeping it in Open Questions ("scope-minimization review") rather than asserting it as settled, so no action needed here beyond flagging it for architect's attention.)

All three resolutions are internally consistent everywhere they recur in the document.

### 4. Completeness — ISSUE (Significant, see #1 above)

All required brief sections are present with no TODO/TBD placeholders, and every Beast Mode decision has a recorded rationale. The gap is narrower than "missing a section" — it's that the brief's own testability claims outrun its fixture spec:

- §5 states specific, checkable metrics: "median time from sign-in to completed transfer < 5 minutes for **a 50-post course**" and "batch engine throughput such that **a 50-post course** transfers in under ~2 minutes."
- §6 item 12 and §7 "Other constraints" state the mock must simulate: the 20-attachment cap, HTTP 429 rate limiting, and rubric license-tier denial — and item 12 closes with "**every behavior above must be fully specified and testable against this layer**."
- But the only fixtures explicitly guaranteed to exist are the **three pre-flight scenarios** (healthy / trashed-deleted / permission-locked), and §5's own "v1 acceptance bar" paragraph narrows the pass/fail criterion to exactly those three scenarios plus summary-report reconciliation.

Nothing in the brief guarantees a 50-post fixture course exists to validate the throughput metric, a 21+-attachment post exists to validate the cap-and-append behavior, a 429-triggering condition exists to validate backoff, a license-tier-restricted course exists to validate rubric degradation, or that fixture posts span all three states (Draft/Published/Scheduled) named in item 4. This is exactly the kind of gap the mock-first directive is designed to prevent — a behavior that's "in scope" and "must be testable" but has no fixture obligated to exercise it.

**Fix:** Add an explicit fixture manifest (even a short list) enumerating what the seeded data must include, and widen §5's acceptance-bar sentence to reference that full list rather than only the three pre-flight scenarios — e.g., "100% pass across all pre-flight scenarios, the 50-post throughput course, the attachment-cap course, the rate-limit-simulation course, and the rubric-license-denial course."

### 5. Quality & clarity — mostly PASSES, one minor issue (#4 above)

Decisions vs. assumptions vs. open questions are well separated and each Decision states its own rationale — this is the brief's strongest quality trait. One inconsistency: the Open Questions list includes "Whether archived courses should also be allowed as targets (v1: no — active targets only, per PRD)" — this has already been decided ("v1: no"), so it reads as a self-answered question rather than a genuinely open one. It should either move to Decisions/Assumptions, or be reworded to state what would actually reopen it (e.g., "candidate to revisit post-v1 based on user feedback").

### 6. Omissions — ISSUE (Significant, see #2 above; also covers #1)

Item 1 ("Sign-in & account handling") makes forced account selection (`prompt=select_account` semantics, to "avoid multi-account collisions") an explicit in-scope v1 behavior. But how this is validated against the mock is left in the **Assumptions** section as an unverified premise: "Mock teacher accounts can adequately represent multi-account collision (forced account picker) without real Google sessions" — with no detail on whether the mock identity layer actually seeds ≥2 selectable mock accounts, or what the mock "account chooser" screen is supposed to look like. Given this is a named in-scope feature (not a follow-on), it shouldn't rest on an unresolved assumption — UX needs a concrete answer to design the sign-in surface, and QA/QC need it to write an acceptance scenario for "collision avoided." Recommend the PM either (a) confirm as a decision that the mock identity layer seeds at least two mock teacher accounts specifically to exercise the forced-picker flow, or (b) explicitly narrow the v1 claim to "the picker UI is built and demonstrable, but multi-account collision avoidance itself is not mock-testable and moves to the follow-on's live-API test list." Either is fine — leaving it as an untouched assumption is not, since it's the only place in the brief where an in-scope feature's testability is genuinely undetermined.

### 7. Errors — ISSUE (Significant, see #3 above)

Item 5, "Post transformation rules," states as one rule set applying across all of item 4's four coursework types (Assignments, Quiz assignments, Questions, Materials): "titles, instructions/descriptions, max points, and topic assignment preserved" and "due dates and scheduled times cleared." This isn't quite accurate as a uniform rule — CourseWorkMaterial (Materials) has no `dueDate`/`dueTime` field and no `maxPoints` field in the underlying data model, and Questions carry additional fields (multiple-choice options / short-answer config) that Assignments don't. Stating the rule as if every field applies to every type risks the engineer building one generic transform instead of a per-type field map, and risks the mock's fixture data model omitting the type-specific fields altogether. This doesn't require a big rewrite — one clarifying sentence closes it: "fields not present on a given type (e.g., Materials have no due date or max points) are simply not set; this rule applies per available field, not uniformly across types."
