## Issues found (by criterion)

### 1. Errors — fallback-note "exact and non-negotiable" string not shown correctly in its own reference mockup (Significant)
§4 states the fallback note text is "exact and non-negotiable" per brief §6 item 8:
`[Classroom Copier Note: Original attachment '<name>' could not be linked due to a permission error or deleted file.]`

But the mockup's own itemized-log demonstration of this exact row (Essay 1 → Fallback) renders:
`[Classroom Copier Note: Original attachment could not be linked…]`

— missing the `'<name>'` filename placeholder entirely, and truncating the rest of the sentence ("due to a permission error or deleted file") with an ellipsis. This is the flagship demonstration of a string the doc itself calls non-negotiable, in the mockup explicitly positioned as "a living style reference for architect/engineer." As written, an engineer copying from the mockup would ship a wrong/truncated string.

**Fix:** render the full exact string in the mockup's example row (widen the Note column or allow wrapping — don't truncate this one), or if column-width truncation is an intentional UI pattern for the Note column generally, say so explicitly and clarify it doesn't apply to fixture-mandated exact strings.

### 2. Omissions/Errors — per-type field differentiation is claimed but not implemented anywhere (Significant)
§3 states: "the itemized log and any per-post detail view render only the fields that type actually has (Materials never show a due-date/points column value; Questions show their answer-config in the Note column) — never a padded/uniform row shape across types."

The actual log table — both as described in §3's own Completion Summary paragraph and as built in the mockup — has exactly five generic columns for every row regardless of type: Title / Type / Topic / Outcome / Note. There is no Due Date or Max Points column anywhere to differentiate, and the mockup's own Question row ("Discussion Q1 | Question | (none) | Transferred | —") shows Note = "—", not an answer-config value as explicitly promised in the same document. This is precisely the risk flagged in the review brief: the ledger metaphor decorates one generic "post" row shape rather than genuinely accommodating four different coursework shapes (Material: no due date/points; Question: answer-config; Assignment/Quiz: due date + points). Note this overlaps with — but is distinct from — a gap the UX critic (pass 1) already flagged at the UX level; it recurs here because the UI doc makes its own affirmative, unhedged claim that the mockup then contradicts, and it isn't listed among this stage's own Deltas.

**Fix:** either (a) add real per-type behavior — a conditionally-rendered Due Date/Points column and a populated answer-config Note for the Question row — to the mockup and keep the doc's claim, or (b) scope the §3 claim down to only what's actually specified/shown (e.g., defer per-type field display to a per-post detail view that doesn't yet exist) so the doc stops asserting something neither the doc's own table structure nor the mockup delivers.

### 3. Errors — "reused verbatim" component claim contradicted by the mockup (Significant)
§3 states the duplicate-run notice is a "shared 'in-the-moment narration' component ... reused verbatim across Selection, Ready-to-Transfer, and Batch Transfer Progress." The mockup shows two different sentences for what's claimed to be the same verbatim component:
- Screen 3 (Selection): "Running the same copy more than once creates duplicate drafts — Classroom Copier does not check for existing copies yet."
- Screen 4c (Ready to Transfer): "Running this copy again later will create duplicate drafts — this check does not exist yet."

Since the mockup is explicitly positioned as "a living style reference," this hands engineering two different strings for a component the doc says is identical, undermining the reference's reliability generally.

**Fix:** pick one exact sentence and use it in both mockup instances, or if intentional variation across screens is actually wanted, correct the doc's "verbatim" claim to describe the variation rule.

### 4. Omissions/Accessibility — "Skipped" outcome is undemonstrated and unstyled in the Completion Summary log (Significant)
The doc (§3, §6) and the UX wireframe both establish three log-row outcome kinds — Transferred / Fallback / Skipped — filterable in the itemized log, and the sample run's own reconciliation line has exactly 1 skip. But in `ui-mockups.html`:
- The stylesheet defines `.outcome-transferred` and `.outcome-fallback` pill classes, but **no `.outcome-skipped` class exists anywhere**.
- No log-table row demonstrates a Skipped outcome (the slate-600/`icon-skip` treatment only appears in the live progress ticker, a different component).

This is the highest-value surface named in the review brief (the Completion Summary), and it fails to visually demonstrate or style the one outcome state most tied to teacher agency and the zero-silent-drop guarantee. An engineer building "off the design tokens... as CSS custom properties" (per the Mockups section) has no sanctioned pill style to reach for here and would have to invent one.

**Fix:** add an `.outcome-skipped` pill style (e.g., slate-600 text on paper-1/line-strong border, consistent with the badge system used elsewhere) and a sample Skipped row in the log table.

### 5. Accessibility — Action Sheet Modal conflates "recommended" with "selected/checked" in the radio styling (Significant)
§6 asserts "every radio/toggle state has a visible shape change, not just a fill-color change." The mockup's CSS defines only two radio appearances: a plain hollow circle (`.option .radio`) and a filled-teal-with-ring circle tied to the `.recommended` class (`.option.recommended .radio`). There is no separate `.selected`/`:checked` state independent of "recommended" — so a user who picks the *non-recommended* option (e.g., "Skip Assignment," "Link Existing File") has no defined visual "this is now chosen" treatment distinct from an unselected hollow radio, while the recommended row's filled/ring style is permanently tied to the static "recommended" label regardless of what's actually selected. This conflates a per-row label (recommended) with a dynamic interaction state (checked) — a real gap in the "visible shape change, never color alone" claim, on one of the two surfaces the review brief called out as highest-complexity.

**Fix:** define an explicit checked-radio style independent of the recommended-badge styling (e.g., a filled ink/teal dot that appears on whichever row is actually selected), so selection state is visible no matter which option the user picks.

### 6. Clarity — "Next handoff" note blurs "reconciling" vs. "reported" fields (Minor)
The Next Handoff section tells the architect: "The Completion Summary's four counts (topics, drafts transferred, fallback shells, rubric notes added) plus skips must be modeled as five distinct, **independently reconciling** fields." But topics and rubric-notes are not actually part of the reconciliation arithmetic (39 + 2 + 1 = 42 uses only drafts transferred + fallback shells + skips); rubric-notes is explicitly called a "non-additive subset tag" elsewhere in this same document. Calling all five fields "reconciling" in the architect-facing handoff risks the backend data model treating topics/rubric-notes as values that must balance against the post total, when they don't.

**Fix:** reword to something like "five distinct fields the backend must expose — three of which (transferred/fallback/skips) must sum to total posts scanned; topics and rubric-notes are independently reported, non-additive counts."

### 7. Quality — minor token drift between doc and mockup CSS (Minor)
`.notice` and `.rate-banner` text color is hardcoded to `#5C3D00` in the mockup CSS, not the documented `--amber-700` token (`#8A5A00`). Not a contrast problem (measured 8.54:1, well above AA) — just a small inconsistency for a mockup framed as token-driven ("doubles as a living style reference"). Worth a token cleanup pass so the CSS is actually authoritative before engineer treats it as such.
