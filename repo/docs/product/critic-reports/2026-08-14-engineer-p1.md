# P0 findings (blocking)

## P0-1 — A post that was successfully created is recorded as `skipped`/`provider_error` with `targetPostId` nulled. **APPLY**

*Criterion 4 (correctness), 9 (oversights). This is prior-P0-5's failure mode, reintroduced inside the fix for prior-P0-3.*

`processItem`'s catch (`server/src/services/transfer-engine.ts:399–415`) is the clause that makes the outcome function total. It is also unconditional: it fires for **any** throw anywhere inside `transferPost`, including after the provider create has already succeeded and the item has already been finished as `transferred`. And `finish()` nulls the evidence on the way past:

```ts
// transfer-engine.ts:775
targetPostId: data.targetPostId ?? null,
```

Three reachable paths run **after** `created.id` exists and `finish({outcome:'transferred', targetPostId: created.id})` has been written:

| Line | Call | In a try? |
|---|---|---|
| `613` | `await this.clearPause(item)` — two Prisma writes | no |
| `705` | `await this.provider.getRubric(post.sourceId)` inside `copyRubricIfAny` | **no** — the `try` starts at 707, around `createRubric` only |
| `554`/`556` | `updateCourseWork*Description(created.id, amended)` on the rubric-degraded path | no |

Any of these throwing — a `SQLITE_BUSY`, a `PermissionError` on the rubric read, a failed description patch — lands in the catch at 399 and produces:

```
outcome: 'skipped', skipReason: 'provider_error', targetPostId: null,
note: 'Could not be copied (…). Nothing was written to the target course for this post.'
```

The note is a **factual falsehood** — the post is in the target course — and it is the same falsehood prior-P0-5 was raised about, one bucket over. The reconciler cannot repair it because the item is terminal, not `pending`. The teacher reads "nothing was written," goes and creates it by hand, and gets the duplicate the whole no-auto-resume decision exists to prevent.

`test/quality/totality.budget.test.ts` does not cover this: all three injected errors are mocked onto `createCourseWork`/`createCourseWorkMaterial`, i.e. **before** the post exists, and the fourth injects at `listTopics`. The gate proves totality (zero pending). It does not prove honesty, which is what prior-P0-5 was about.

**Fix.** Make the catch evidence-aware. Read the item's current `outcome`/`targetPostId` before overwriting; if `targetPostId` is already set, keep `transferred`/`fallback_shell` and append the failure to `note` instead of re-bucketing. Give `finish()` an optimistic predicate — `updateMany({ where: { id, outcome: 'pending' }, … })` — so overwriting a terminal outcome is not expressible at all, and log loudly when the update affects 0 rows. Additionally move `getRubric` inside `copyRubricIfAny`'s try, and wrap the post-create block (rubric copy + description amendment) in its own try that degrades to a note rather than propagating. Add to the totality budget: inject a throw from `getRubric` and from `updateCourseWorkDescription` and assert the item stays `transferred` with `targetPostId` intact.

## P0-2 — The interval reconciler can race a live executor. No lease, no mutual exclusion, every write unconditional. **APPLY**

*Criterion 4 (correctness), 7 (risk/operability). I asked this question directly; the answer is that nothing prevents it.*

`JobReconciler.reconcileStaleJobs` selects on `status IN ('queued','running') AND lastHeartbeatAt < cutoff` (`job-reconciler.ts:58–61`). Staleness is the **only** predicate. There is no executor lease, no owner/epoch/pid column, no `version` column — I grepped `server/src` and `schema.prisma` for all of them and found none. Every executor write is an unconditional `update where: { id }`.

So when a live executor's heartbeat goes stale, the reconciler runs concurrently against the job it is executing, and:

1. It rewrites the job's `pending` items — including the one the executor is mid-flight on — to `skipped`/`server_interrupted` or (worse) to `transferred` by title match.
2. It sets `status: 'interrupted'`, `finishedAt`, and **`activeAccountId: null`** (`76–84`).
3. The executor keeps going. It read its `items` list into memory once at line 263, so it processes every item regardless of what the reconciler just wrote, and `finish()` overwrites each reconciler verdict.
4. At the end the executor writes `status: 'completed'` over `interrupted` and `finishedAt` a second time (296–307).

Two consequences are severe, not cosmetic:

- **The single-active-job guard is released while the job is still running.** Between step 2 and step 4 the account has no active job as far as the unique index and `GET /transfer-jobs/active` are concerned, so a second `POST /transfer-jobs` succeeds and a second executor starts writing into the same target course. That is duplicate posts, produced by the mechanism built to prevent them.
- **The reconciler can mark an item `transferred` for a post the executor has not created yet, and the executor then creates it** — a duplicate with a `targetPostId` pointing at the wrong thing.

Reachability is not theoretical. `jobStaleAfterMs` defaults to 60s and the reconciler fires every 30s (`config.ts`). The heartbeat is written per item and around rate-limit sleeps, but **not** during `buildTopicMap` (which creates every topic in a loop, line 346–361) and **not** during the `enumeratePosts` hydration at line 255. With `MOCK_PROVIDER_DELAY_MS` — a variable `config.ts` explicitly documents as "for driving the deployed app by hand" — a 50-post course's enumeration alone exceeds 60s at a 1s delay. The very configuration the doc offers for demoing the product is the one that trips this.

**Fix, three parts.** (a) Add an executor lease: a `TransferJob.executorId` (or `leaseToken`) column set at `execute()` entry; every executor terminal write becomes `updateMany({ where: { id, executorId: mine } })`, and the executor aborts if it affects 0 rows. (b) Have the reconciler claim a job before touching it — `updateMany({ where: { id, status: {in:['queued','running']}, lastHeartbeatAt: { lt: cutoff } }, data: { status: 'interrupted', executorId: null } })` — and skip the job if the claim affects 0 rows. (c) Heartbeat inside `buildTopicMap` and around the hydration enumeration so a slow-but-alive job is never mistaken for a dead one. Gate it: start a job with a `sleep`-injected executor, run the reconciler mid-flight, and assert exactly one of the two writes the terminal state and the invariant still holds.

## P0-3 — `copyAttachmentToMyDrive` mutates the **source** attachment in place. The product's one promise about the source course is broken. **APPLY**

*Criterion 4 (correctness), 6 (seam integrity). Data integrity, and an undisclosed mock/real divergence.*

`mock-classroom-provider.ts:305–318`:

```ts
const newDriveFileId = `${row.driveFileId ?? row.id}-copy-${actingAccountId}`
await this.prisma.mockAttachment.update({
  where: { id: ref.id },
  data: { driveFileId: newDriveFileId, ownerAccountId: actingAccountId, driveState: 'healthy' },
})
```

`ref.id` is the **source course's** attachment row. The method named "copy" is implemented as a **move**: it rewrites the source post's attachment to point at the copy, reassigns its owner, and flips its health to `healthy`.

This is the only write to the source course anywhere in the system, and the product's whole proposition is that copying is non-destructive. Concretely:

- The teacher's original post in the source course now links a different Drive file than it did before they ran a *copy*.
- The pre-flight finding disappears: re-scanning the same source course no longer flags that attachment as `permission_locked`, because the mock healed it. F3's scenario is not reproducible within a session.
- The engine is *built on* the move semantics — `transferPost` (`486–498`) calls `copyAttachmentToMyDrive`, then `refreshAttachments(post)` re-reads **the same source rows** and links the same attachment ids. A `RealClassroomProvider` implementing the honest copy (`drive.files.copy` → a new file id, source untouched) would return `newDriveFileId` into a caller that ignores it, and the created post would link the original locked file — silently defeating the Scenario-3 recommended option.
- The `{ newDriveFileId }` return value is discarded at every call site. A return value nothing reads is the signature of a contract that was satisfied by mutation instead.

The engineer disclosed "no live Google integration, so port fidelity is asserted not verified." This is not that. This is the mock implementing a *different operation* than the one the port names, with the engine depending on the difference — a divergence discoverable without any live integration, and not disclosed.

**Fix.** Make the mock a copy: insert a **new** `MockAttachment` row owned by `actingAccountId` with `driveState: 'healthy'`, leave the source row untouched, and return its id. Have `transferPost` collect the returned ids and substitute them into the materials payload rather than re-reading source rows and hoping. Add a contract-test assertion that after `copyAttachmentToMyDrive` the source attachment's `ownerAccountId`, `driveFileId` and `driveState` are **unchanged** — that assertion is the whole guarantee, and it currently does not exist.

## P0-4 — The interruption evidence check matches on title alone, against a target course that is never pruned. It manufactures false "transferred" verdicts. **APPLY**

*Criterion 4 (correctness). This is the mechanism prior-P0-5 was fixed with, and it is unsound.*

`job-reconciler.ts:156–179` builds the target index as `Map<"sourceType:title", postId>` and matches at line 127 with `targetIndex.get(\`${item.sourceType}:${item.title}\`)`. My prior report specified matching on **title + `createdOrder`**; `createdOrder` was dropped, and nothing replaced it.

Three ways this returns a false positive, i.e. reports a post as copied that was never copied:

1. **The target course is not empty.** UX permits transferring into an existing course. Any pre-existing target post whose title collides with a source post makes that item `transferred`, backfills a `targetPostId` pointing at a stranger's post, and tells the teacher a post arrived that never did. That is a silent drop reported as a success — the exact class of failure the whole reconciliation edifice exists to make impossible.
2. **The seed never prunes posts created by earlier runs.** `seedFixtures` upserts by stable id (correctly idempotent — I verified) but has no cleanup for the generated `MockCourseWork`/`MockCourseWorkMaterial` rows a transfer creates. Target courses accumulate across boots, so on the **second** run of the same transfer the target already contains a post with every source title. Every interrupted item then verifies as `transferred`, unconditionally.
3. **Duplicate titles within a course.** `index.set` keeps the last writer, so N source posts sharing a title all resolve to the *same* `targetPostId`, and nothing detects that two items claim one post. Nothing scopes the index against ids already claimed by sibling items in the same job, even though `targetPostId` is right there.

The budget test does not catch any of this because it constructs the happy case: `job-reconciler.budget.test.ts:40–50` creates a target post with `title: attemptedPresent.title` and then asserts `itemsVerifiedTransferred === 1`. It proves the matcher matches. It does not probe whether the match means anything.

**Fix.** Verify against evidence the job itself owns, not against the target course's namespace. Options in order of preference: (a) write `targetPostId` **before** the outcome — a `claimedTargetPostId` set immediately after `issueCreate` returns — so recovery reads an id instead of guessing from a title; (b) failing that, restrict the index to posts in the target whose `creationTime >= job.startedAt`, match on `(sourceType, title, createdOrder)`, and **exclude ids already claimed by any sibling item in the job**; and when more than one candidate matches, resolve to `skipped`/`server_interrupted` rather than guessing. Extend the gate with the three false-positive cases above — a pre-existing colliding post, a second run into a dirty target, and two source posts sharing a title — and assert none of them yields `transferred`.

## P0-5 — The failure path prior-P0-3 created has no working recovery: Retry is a no-op and the poll loop is permanently dead. **APPLY**

*Criterion 4 (correctness), 7 (operability). The fix made `status: 'failed'` reachable; nothing gets the user out of it.*

Confirmed in the client:

- `client/src/lib/api-client.ts:375–388` — `pollJobStatus`'s `tick()` calls `onError` and **returns without rescheduling** on any fetch or `ApiValidationError` failure. One transient blip during a transfer stops all progress updates permanently. `api-client.test.ts:246–255` asserts this behaviour rather than flagging it.
- `client/src/App.tsx:255` wires `TransferProgress`'s `onRetry` to `() => setStage('transfer')`, but `TransferProgress` renders its own terminal error UI while `stage` is *already* `'transfer'` (`TransferProgress.tsx:130–138`). Setting state to its current value is a React no-op: no remount, no reset of local `status`, no restart of the loop. **Clicking Retry does nothing.**
- No test exercises the click; `transfer.test.tsx:197–205` only asserts the error UI renders.

There is no mid-transfer cancel in v1 (UX Decision 13), so a user who reaches `failed` — or who simply loses one poll — is on a frozen screen with one button that does nothing. This is the same dead-end prior-P0-3 was raised about, moved from the server to the client.

**Fix.** Give the poll loop bounded retry with backoff before it gives up (3 attempts, then surface the error), and make the poll resumable rather than one-shot-fatal. Make Retry actually re-enter: remount `TransferProgress` via a `key` bump, or expose a `restart()` the error state calls, and reset local `status`. If the job is genuinely `failed`, route back to Selection with the failure explained rather than offering a Retry that cannot succeed. Test the click, not just the render.

# Significant findings — APPLY

## Criterion 6 — Seam & interface integrity

**A. `shareMode: a.shareMode ?? 'VIEW'` — the prohibited default, under a comment asserting it cannot happen.** `transfer-engine.ts:438–440`:

```ts
// Copied, never defaulted. The union makes shareMode required here,
// so there is no path that silently substitutes VIEW.
shareMode: a.shareMode ?? 'VIEW',
```

The comment states the inverse of the line beneath it. The brief's binding requirement is "preserve each attachment's `shareMode` … **never default to VIEW**." `MockAttachment.shareMode` is `String?`, the seed type is `'VIEW'|'EDIT'|'STUDENT_COPY'|null`, and the mock's mapper is `(row.shareMode as ShareMode|null) ?? null` — so `null` is representable at three layers, and the engine's answer to it is the one substitution the brief forbids. Making the field required *on the payload union* (APPLY-C's mechanism) is correct and does travel end to end — I verified the carriage works and `transfer-engine.test.ts:370` proves `STUDENT_COPY` survives — but it forced the caller to produce a value, and the caller produced the forbidden one. Today all 10 `driveFile` fixtures set `shareMode` (I checked every literal), so this is latent, not live; a real Drive file with an unset shareMode reaches it immediately. **Fix:** make `ProviderAttachment.shareMode` non-nullable for `kind: 'driveFile'`, or treat a null as a finding — never a substitution. Add a fixture with a null `shareMode` and assert the engine does not write `VIEW`.

**B. Three modules reach around the type-only port into the mock's tables.** The port emitting no JS was the run's chief structural device, and it is bypassed at three sites: `transfer-engine.ts:563` (`prisma.mockAttachment.findMany` in `refreshAttachments`), `routes/transfer-jobs.ts:201` (`prisma.mockCourseWork.findMany`), `preflight-engine.ts:100–101` (`prisma.mockCourse.findUnique`). The first is the serious one: `refreshAttachments` is how every attachment reaches `materials[]`, so when `RealClassroomProvider` ships, that query hits a table that no longer exists and **every post is created with zero attachments** — the single highest-fidelity read in the product, routed around the seam built to protect it. The `dependsOn` graph and the "only the composition root touches a concrete provider" claim are both true of *imports* and false of *data access*. **Fix:** route all three through the port (`getAttachments(refs)` / `getCourse(id)`), and add a lint rule or a test asserting no `prisma.mock*` reference outside `adapters/mock/` and `fixtures/`.

**C. A `PreflightScan` can be replayed into a second job — sequential duplicate transfer.** `createTransferJob` checks only for a *non-terminal* job on the account. Nothing marks a scan consumed and `TransferJob.scanId` is not `@unique`, so re-POSTing the same `scanId` after the first job completes creates a whole second job and copies every post again. Item ids are `${jobId}-i${n}`, so there is not even an id collision to stop it. Back-button-then-confirm is enough. **Fix:** `scanId String @unique` on `TransferJob` (making replay unrepresentable, at the cost of one word) or an explicit `consumedAt` on the scan, returning `409 scan_already_used`.

**D. `SCHEDULED` is a mock-invented `CourseWorkState` with no real-API counterpart — an undisclosed divergence, now locked in by a contract test.** `ALL_COURSE_WORK_STATES = ['DRAFT','PUBLISHED','SCHEDULED']` is passed to both surfaces. To my knowledge the real `courses.courseWork.list` `courseWorkStates` enum is `PUBLISHED | DRAFT | DELETED` (a scheduled post is a `DRAFT` carrying `scheduledTime` — which `MockCourseWork` *also* models, so the same fact is stored twice), and `courses.courseWorkMaterials.list` takes a differently-named `courseWorkMaterialStates` over a different vocabulary. I cannot verify this against a live API and do not assert it as fact — but the shape of the finding stands either way: `QUIZ_ASSIGNMENT` was correctly identified as mock-only and flagged, and `SCHEDULED` is exactly the same kind of thing and was not. `classroom-provider.contract.test.ts:58–65` now asserts `states.has('SCHEDULED')`, which pins the divergence in place as though it were fidelity. **Fix:** either map `SCHEDULED` to `DRAFT + scheduledTime` at the port boundary, or flag it in `05-implementation.md` §7 and on the backlog beside `QUIZ_ASSIGNMENT`. Split the two surfaces' state parameters so a single `ListCourseWorkRequest` is not asserting one vocabulary for two different real endpoints.

**E. `/transfer-jobs/:id/items` re-reads live source rows for data the item already persisted.** `routes/transfer-jobs.ts:200–217` queries `mockCourseWork` for `workType`, `maxPoints` and `answerConfig`, even though `TransferJobItem.workType` was copied from the scan at job creation (`transfer-engine.ts:108`) and is sitting on the row. This is the two-measurements pattern in miniature, inside the ledger the whole run is about: a post deleted from the source after the transfer loses its `workType`, and `typeLabel` then relabels a Question as **"Assignment"** in the completion log; a `maxPoints` edited after the transfer is displayed as though it were what was copied. **Fix:** render from `row.workType` and persist `maxPoints`/`answerConfig` onto `PreflightScanItem` at scan time. The immutable record is the point.

## Criterion 4 — Correctness & soundness

**F. The rate-limit shell discards every trace of the attachments it dropped, including the 21+ overflow URLs.** `transfer-engine.ts:638–647` composes the shell's description as `{ overflow: [], notes: [rateLimitExhaustionNote] }` — so the attachment-fallback notes accumulated for that post and the overflow link list are both thrown away, and the shell says "re-attach any files" without naming one. For a 25-attachment post this is the 21+-as-description-URLs guarantee silently voided on the fallback path. **Fix:** carry `notes` and `overflow` into the shell's description; the links are free and they are the only thing that makes "re-attach any files" actionable.

**G. `enforceRateLimit` matches on post **title**, globally.** `mock-classroom-provider.ts:325–332` keys the simulation on the title string, so any post anywhere named `F13_PERSISTENT_429_TITLE` 429s — including one created in a *target* course by a previous run. Combined with the un-pruned target (P0-4), a second run's create into the target can trip a rule intended for one source fixture. **Fix:** key the rule on the source post id, or scope it to the source course.

**H. `?outcome=` on `/items` is passed to Prisma without validating against the closed vocabulary.** `routes/transfer-jobs.ts:192–196` forwards an arbitrary query string into the `where` clause. Not injectable (Prisma parameterises) and read-only, so impact is low — but it is a documented instance of a closed vocabulary crossing the application boundary unparsed, in a codebase whose stated discipline is that zod is that boundary. **Fix:** `OutcomeSchema.safeParse` it; 400 on failure.

**I. The scan is a snapshot and the user is never told.** Per the P0-2 fix, a post added to the source between scan and confirm is correctly excluded from the job — but the Completion Summary then reads "N of N" with no indication that N was measured earlier and the course has since changed. There is no scan TTL, no `scannedAt` freshness check at `POST /transfer-jobs`, and nothing re-scans. The behaviour is right; the silence about it is a small honesty gap in a product whose thesis is the opposite. **Fix:** reject or warn on a scan older than a threshold (10 min), and put "Scanned at HH:MM" on Ready-to-Transfer.

**J. `orderingKey`'s tiebreak is `sourceId`; the schema says it is `createdOrder`.** `schema.prisma` documents `MockCourseWork.createdOrder` as the "deterministic tiebreak companion to creationTime — see post-enumerator," and `post-enumerator.ts:69–75` tiebreaks on `sourceType` then `sourceId` and never reads the column. The ordering *is* a genuine total order either way (I verified the reversal test at `post-enumerator.test.ts` proves totality, and `sortOrder` makes the 1–20 attachment cap deterministic — APPLY-I landed correctly). But the persisted `createdOrder` on the mock tables is now dead data described as load-bearing. **Fix:** pick one and delete or use the other.

## Criterion 7 — Risk & operability

**K. `GET /courses` runs a full two-surface paginated enumeration *per course*, only to compute `postCount`.** `routes/courses.ts:27–41` calls `enumeratePosts(provider, course.id)` inside the course loop — two paginated drains plus an attachment query plus a rubric query for every course the teacher owns. A 30-course teacher pays 60+ paginated scans to render the selection screen, and it is the first authenticated call the app makes. No budget covers it (`perf-f4` measures the engine only). **Fix:** a `countPosts` on the port, or a cheap count query; and a budget row on the selection-screen call.

**L. `seedOnBoot` defaults to true in production and never prunes.** `config.ts`: `process.env.SEED_ON_BOOT !== 'false'` — production boots seed fixture data. Idempotent, so harmless in itself, but it never removes the posts a transfer created, which is the accumulation that makes P0-4 fire. **Fix:** default `seedOnBoot` to false when `isProductionLike`, and give the seed an explicit reset path for generated rows.

**M. In-flight requests are never aborted on unmount; the cold-start overlay can outlive its screen.** The `AbortController` in `api-client.ts:173,192` is tripped only by the internal 60s ceiling; no caller aborts from a cleanup. Components guard with local `live` flags instead, so React is quiet but the `fetch` runs on and the global `slowRequests` counter (`114,179–180,216–219`) is not decremented until it settles — leaving the global `ColdStartOverlay` visible after the screen that triggered it is gone. **Fix:** return the controller and abort in each effect's cleanup.

**N. `me()` and `getActiveJob()` failures are swallowed indiscriminately.** `App.tsx:102` catches *every* rejection from `me()` as "no session" — a 5xx or a validation failure silently parks the user on the sign-in screen with no feedback. `App.tsx:97` treats any `getActiveJob()` failure as "no active job," so a blip during boot drops the user on Selection while a job is still running server-side, defeating the F12 reconnect guarantee that file's own header describes. **Fix:** distinguish 401 (no session) from every other failure and surface the rest.

**O. No React error boundary anywhere in the client.** All error handling is `.catch()` into state; a synchronous render-time throw in any screen is an unrecoverable white page. **Fix:** one boundary at the app shell rendering `ErrorState`.

## Note for `project-profile.md` → `## Lessons learned`

> **A total function is not the same as an honest one.** The outcome function was made total by wrapping the item in one broad `try/catch` — and that same clause, being unconditional, now overwrites correct terminal outcomes with false ones and nulls the evidence on the way past. Totality closed the arithmetic and re-opened the lie the arithmetic was there to prevent. When adding a catch-all to close an invariant, check what it does to the paths that had already *succeeded*, and give the write an optimistic predicate so "overwrite a terminal state" is unrepresentable rather than merely unintended.

> **Recovery-by-inference needs evidence the job owns, not evidence the world happens to contain.** Interruption recovery was fixed by verifying against the target course — matching on title, in a namespace shared with pre-existing posts, prior runs, and duplicate titles. The mechanism is right and the key is wrong, and the gate proved the mechanism rather than the key. When a check exists to distinguish "we did this" from "this exists," write the test that tries to fool it: seed the collision first, then assert the check refuses.
